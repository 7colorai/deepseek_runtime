# 托管路线图

> ❓ **我现在能用这个运行时做 SaaS 服务吗？**  
> 💡 不能。v0.1.1a1 是**本地运行时内核**，不是托管服务平台。这篇文档告诉你为什么、以及未来怎么走。

---

## 当前版本不包含什么？

❓ **那这个版本到底少什么？**  
💡 目前你能拿到的是一个可以在你本地（或你服务器上）跑 Agent 的 Python 库。但以下这些东西，它不是开箱即用的：

- ❌ 多租户 API 服务器
- ❌ 请求队列
- ❌ 租户隔离（你的用户 A 和用户 B 的数据是分开的吗？）
- ❌ 云密钥管理集成
- ❌ 托管计费
- ❌ Web 管理面板
- ❌ 企业策略中心

> 🎯 **设计哲学**：先做好一个事的"内核"，再把服务层包在外面。这避免了运行时内核被部署决策过早耦合。

---

## 未来托管服务的样子

❓ **那你们打算以后怎么加托管能力？**  
💡 分五个阶段，从安全设计到公开上线：

| 阶段 | 工作内容 |
| --- | --- |
| 🏗️ **H1 — 安全与架构设计** | 定义托管威胁模型、租户边界、密钥存储、审计留存、速率限制策略 |
| 🧩 **H2 — 服务适配层** | 在 `DeepSeekRuntime` 外面加一层服务适配器，**不改内核 API** |
| 🛡️ **H3 — 增强沙箱** | 在工作区工具外面加 OS/容器级沙箱 |
| 📊 **H4 — 托管可观测性** | 增加托管环境下的可观测性导出和计费对账 |
| 📖 **H5 — 公开 API 文档** | 提供服务层 API 文档和兼容性测试 |

## 现在你应该怎么做？

❓ **我要做产品，等你们托管还是自己搞？**  
💡 两个选择：

- **短期 / 单个用户**：直接用本地运行时内核。你自己起一个 Python 进程或 FastAPI 包装一层就可以了。
- **长期 / 多租户产品**：先把有状态的托管代码放在**这个仓库外面**，或者单独做一个 service package。等 H2 阶段的服务适配层出来后，再考虑合并。

> 💡 关键原则：**不要让部署方式污染核心引擎。** 即使未来加了托管能力，`DeepSeekRuntime.run()` 的签名不会变——你的集成代码不用重写。

## 对 PM 的时间线预期

❓ **这些阶段大概要多久？按什么节奏？**  
💡 目前没有承诺具体日期，但可以告诉你几点：

- **H1（安全设计）** 是**必须做对才能往下走的**——多租户 Agent 的安全问题和传统 Web 应用完全不同（Agent 会读写文件、执行命令、改代码）。这个阶段急不得。
- **H2-H3** 可以并行推进，因为它们分别关注"服务层"和"安全层"。
- **H4-H5** 是面向客户的能力，通常在 H2-H3 稳定后启动。

**目前最佳策略**：如果你是多租户场景，先在外部构建你的服务层，同时关注这个路线图的更新。等 H2 发布后评估迁移成本。

## 相关引用

本路线图的设计逻辑受到以下研究的影响：

- **Paper A2 — AIOS (COLM 2025)**：AIOS 提出的"LLM 内核 + 服务层"分层架构是本路线图最直接的理论基础。AIOS 强调操作系统内核不应该耦合用户态的服务策略——这和本运行时"内核不变、外包服务层"的思路完全一致。
- **Paper A1 — Agent Harness Survey**：对现有 Agent 托管方案的横向比较表明，**过早耦合部署架构会导致内核难以进化**。本路线图的 H1→H5 分阶段策略正是为了避免这个陷阱。
- **Paper B1 — ReAct (ICLR 2023)**：即使在托管环境下，Agent 循环的核心逻辑仍然是 ReAct 范式。路线图中的 H2 服务适配层承诺"不改内核 API"，确保了 ReAct 循环的稳定性不受部署方式影响。
- **Paper D1**：多租户 Agent 安全研究为 H1 威胁模型提供了关键输入——Agent 的安全边界不是传统 Web API 的安全边界。
- **Paper B3 / B7**：关于 Agent 系统可扩展性和生产部署的研究，为 H4 的托管可观测性设计提供了参考。
